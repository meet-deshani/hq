# TabDesk

User-defined tables. A person with no access to this repository creates a page,
defines its columns, and starts entering rows — and the API, the grid, the entry
form and the permission checks all follow from that definition.

Excel's grid, Notion's structure, HQ's permissions.

## Why this is not a registry entity

The rest of HQ renders from `backend/registry.py`: one declarative Python list,
read at import time, each entry bound to a real SQLAlchemy model. That design is
what keeps the API, the UI and the CLI from drifting apart — and it is exactly
why TabDesk cannot live there.

A registry entity is decided by a developer at deploy time. A TabDesk table is
decided by a user at 4pm on a Tuesday. You cannot add a row to a Python list
from an HTTP request and have `Base.metadata` notice.

So TabDesk is a parallel subsystem with the same *discipline* and none of the
same *machinery*:

| | Registry entities | TabDesk |
|---|---|---|
| Schema defined by | Python, at deploy | Users, at runtime |
| Storage | One table per entity, real columns | `tabdesk_rows.data`, one JSON blob per row |
| Routes | Generated by `crud.py` from the registry | `backend/tabdesk.py`, generated from column metadata |
| Permissions | Global role → `entity:action` | Global gate **plus** per-table membership |
| Discovery | `GET /api/meta/entities` | `GET /api/tabdesk/tables` |

The shared discipline: **one declarative description drives every consumer.** For
a registry entity that description is a Python dict. For a TabDesk table it is
the `tabdesk_columns` rows. Neither the grid nor the entry modal nor the filter
bar contains per-table code.

## Data model

Five tables. `backend/tabdesk_models.py`.

```
tabdesk_tables ─┬─< tabdesk_columns      the schema, one row per column
                ├─< tabdesk_rows         the data, JSON keyed by column.key
                ├─< tabdesk_members      who may do what, per table
                └─< tabdesk_saved_views  named filter+sort combinations
```

### `tabdesk_tables`

A page in the sidebar. `slug` is what the URL carries; `group_name` is the
sidebar section it nests under, so twelve tables do not become twelve flat
entries. `visibility` is `workspace` or `private` (see Permissions).

### `tabdesk_columns`

`key` is a slug generated from the label on creation and then **never changes**,
because it is the JSON key every existing row is already stored under. Renaming
a column changes `label` only. This separation is the single most important
decision in the schema: keying rows on a mutable label would mean a rename
silently orphaned every value in the column.

`type` is one of the types below. `options` holds the choice list for
`select`/`multiselect`. `ref_kind` + `ref_target` describe a `relation`.

### `tabdesk_rows`

`data` is a JSON object: `{"<column.key>": <value>}`. Values are stored in a
canonical JSON form per type (dates as `YYYY-MM-DD` strings, money as a number,
multiselect as an array), so that sorting and filtering do not have to guess.

A key that has no corresponding column is ignored on read and stripped on write.
That makes deleting a column non-destructive to the other columns, and makes a
re-added column recover its old values.

### `tabdesk_members`

`(table_id, user_id, access)`, unique on the pair. Absence of a row is not
denial — see the default below.

## Column types

Sixteen. Each type is one entry in `TYPES` in `backend/tabdesk_sql.py`, carrying
its JSON coercion, its SQL cast for views and sorting, and the operators its
filters accept.

| Type | Stored as | Notes |
|---|---|---|
| `text` | string | Single line. |
| `longtext` | string | Textarea in the modal; truncated in the grid. |
| `number` | number | |
| `money` | number | Rendered with the org's currency, right-aligned. |
| `percent` | number | Stored as entered (`12.5` is 12.5%), not as a fraction. |
| `date` | `YYYY-MM-DD` | Lexicographic sort is chronological — deliberate. |
| `datetime` | ISO 8601 UTC | |
| `select` | string | Must be one of `options`, or null. |
| `multiselect` | array of strings | Every element must be in `options`. |
| `checkbox` | boolean | Never null; absent reads as `false`. |
| `user` | integer | An HQ `users.id`. Resolved to a name on read. |
| `url` | string | |
| `email` | string | |
| `phone` | string | |
| `attachment` | `{url, filename}` | A **link**, not an upload — matching the platform's existing `attachments.storage_url`. HQ has no upload endpoint; adding one is its own piece of work. |
| `relation` | array of integers | Row ids in another TabDesk table, or record ids of a registry entity. |

`relation` resolves `ref_kind`:

* `ref_kind="tabdesk"`, `ref_target="<table id>"` — link to rows of another TabDesk table.
* `ref_kind="entity"`, `ref_target="<registry key>"` — link to real HQ records: `customers`, `projects`, `tasks`, anything in the registry.

That second form is the point of including relations at all. A TabDesk table is
not a silo; a "Site visits" table can point at the actual Customers a visit was
for, and the label resolves through the registry's `title_field`.

**There is no database-level foreign key.** The ids live inside a JSON array;
Postgres cannot police them. Deleting the target row leaves a dangling id, which
resolves to `(deleted)` on read rather than erroring or being silently dropped.
This is a real, accepted limitation of JSON storage, not an oversight — see
Limitations.

## Permissions

Two layers, both enforced on every route. The UI hides what a user cannot do;
the routes refuse it regardless.

### Layer 1 — the global gate

Standard HQ permissions, derived from the registry the same way everything else
is: `tabdesk:read`, `tabdesk:create`, `tabdesk:update`, `tabdesk:delete`. These
answer "may this person use TabDesk at all, and may they create a new table".
They arrive automatically for existing roles via the wildcard grants in
`permissions.py`.

### Layer 2 — per-table access

Four levels, ordered. Each includes everything below it.

| Access | View rows | Add entry | Edit any entry | Delete entry | Change columns, settings, sharing |
|---|---|---|---|---|---|
| `viewer` | ✅ | | | | |
| `contributor` | ✅ | ✅ | own rows only | own rows only | |
| `editor` | ✅ | ✅ | ✅ | ✅ | |
| `manager` | ✅ | ✅ | ✅ | ✅ | ✅ |

`contributor` is the level Meet described as "can add entry": it is the shape
almost every real data-collection table wants — a field team that files rows
without being able to rewrite each other's. "Own" means `created_by_id`.

### The default, and who overrides it

**A table with `visibility="workspace"` is readable by anyone holding
`tabdesk:read`, without a membership row.** Explicit membership only ever *adds*
capability above that floor.

This follows the rule already written into `permissions.py` — *read is generous,
delete is not* — and it satisfies the standing requirement that Nishant and
Hemish see everything. A table set to `visibility="private"` drops the floor:
only its creator and explicit members see it at all, and it does not appear in
anyone else's sidebar.

Two overrides sit above the whole scheme:

* **Admin** (`tabdesk:*`) is `manager` on every table. Someone has to be able to
  fix a table whose only manager has left.
* The **creator** is permanently `manager` on their own table and cannot be
  demoted out of it by another member, only by an Admin. Without this, two
  managers can lock each other out.

Resolution lives in `backend/tabdesk_access.py` and is the security boundary of
this subsystem. It is tested as a matrix, not by example.

## API

Registered in `main.py` **before** `crud.router`, because that router owns the
catch-all `/api/{key}` and would otherwise match `/api/tabdesk/tables` as
entity `tabdesk`, row `tables`.

```
GET    /api/tabdesk/tables                     pages the caller may see, grouped for the sidebar
POST   /api/tabdesk/tables                     create a table          (tabdesk:create)
GET    /api/tabdesk/tables/{id}                one table: columns, saved views, my access
PATCH  /api/tabdesk/tables/{id}                rename, re-icon, change visibility   (manager)
DELETE /api/tabdesk/tables/{id}                drop the table and its view          (manager + tabdesk:delete)

POST   /api/tabdesk/tables/{id}/columns        add a column            (manager)
PATCH  /api/tabdesk/tables/{id}/columns/{cid}  relabel, retype, reorder, edit options (manager)
DELETE /api/tabdesk/tables/{id}/columns/{cid}  remove a column         (manager)

GET    /api/tabdesk/tables/{id}/rows           filter · sort · group · search · paginate
POST   /api/tabdesk/tables/{id}/rows           add an entry            (contributor)
PATCH  /api/tabdesk/tables/{id}/rows/{rid}     edit an entry           (contributor own / editor any)
DELETE /api/tabdesk/tables/{id}/rows/{rid}     delete an entry         (contributor own / editor any)

GET    /api/tabdesk/tables/{id}/members        who has access          (manager)
PUT    /api/tabdesk/tables/{id}/members/{uid}  grant or change access  (manager)
DELETE /api/tabdesk/tables/{id}/members/{uid}  revoke                  (manager)

POST   /api/tabdesk/tables/{id}/views          save the current filter+sort
DELETE /api/tabdesk/tables/{id}/views/{vid}    delete a saved view
```

### Querying rows

Filters are query parameters of the form `f.<column key>.<op>=<value>`, which
keeps them expressible in a URL, a saved view, and a `curl` line without a
request body.

```
?f.status.eq=Open
?f.amount.gte=50000
?f.name.contains=steel
?f.owner.eq=me                     # resolves to the calling user
?f.closed_on.empty=true
?f.stage.in=Testing,Training       # OR within one column
?sort=-amount&group=status&q=steel&limit=50&offset=0
```

Operators by type: `eq · ne · empty` everywhere; `contains · startswith` on the
string types; `gt · gte · lt · lte` on number/money/percent/date/datetime;
`in · has` on select/multiselect/relation. Filters on different columns AND
together; repeated values within one column OR.

**An unknown column or an operator the type does not support is a 400, never
ignored.** This is the same rule `crud.py` enforces and for the same reason: a
silently dropped filter makes "does this row exist?" answer yes.

## The SQL view

Every table also gets a read-only Postgres view, `tabdesk_v_<id>_<slug>`, which
flattens the JSON into typed columns so pgAdmin, Metabase and plain `psql` can
read a TabDesk table as if it were a normal one. The id is in the name because
`slug` is only unique per organisation, and a second organisation reusing a slug
would otherwise collide with an existing view — which, since a failed rebuild is
deliberately non-fatal, would fail *silently*.

This is the part of TabDesk most likely to break, so it is built defensively:

* **Rebuilt from scratch, never patched.** Every column add, rename, retype or
  delete drops and recreates the view from current metadata. An incremental
  patch path would eventually disagree with the table it describes, and a view
  that disagrees is worse than no view — it looks authoritative.
* **Every cast is NULL-safe.** On Postgres, `(data->>'amount')::numeric` raises
  on an empty string, and one bad cell would break the entire view for every
  reader. Numeric and date casts go through a guard that yields NULL instead of
  raising.
* **Identifiers are never interpolated from user input.** The view name comes
  from the table id and a slug filtered to `[a-z0-9_]`; column aliases are
  quoted and filtered the same way. A user-supplied label never reaches DDL.
* **A failed view rebuild does not fail the request.** It is logged and the
  table still works. The view is a convenience for external readers; the app
  itself never reads it.

On SQLite the views are created too, via `json_extract`, so local dev matches
production in shape. They are untyped and slow there, which does not matter for
a dev database.

**One operational consequence, found by running the suite against a real
Postgres.** A view *depends on* `tabdesk_rows`, so `DROP TABLE tabdesk_rows`
fails with `DependentObjectsStillExist` while any view exists. SQLite does not
enforce that dependency, which means local dev will never reveal it. Any future
migration that alters or drops `tabdesk_rows` must drop the TabDesk views first —
`drop_all_tabdesk_views()` in `tests/tabdesk_postgres_test.py` is the query to
copy. This is a real cost of choosing views, and it is here so the next person
does not discover it during a migration.

## The interface

### Sidebar

TabDesk is a workspace, alongside CRM and Work. Unlike every other workspace in
this shell, **its page list is fetched, not hardcoded** — `workspacesFor()` and
`PRODUCT_WS_TABS` in `home.html` describe a fixed world, and TabDesk's world
changes when a user clicks New table.

```
TabDesk
  ▾ Operations              ← group_name
      Site visits       12
      Vehicle log      308
  ▾ Sales
      Pricing requests   7
  ─────────────
  + New table               ← only with tabdesk:create
```

Row counts come with the list, so the sidebar answers "is there anything in
there" without opening the page. A private table appears only for its members.

### The table page

```
┌────────────────────────────────────────────────────────────────────────┐
│ Site visits                                        [＋ Add entry]      │
│ ── All · Open · This month ──          ⚙ Columns   ⋯ Settings          │
│ ┌────────────────────────────────────────────────────────────────────┐ │
│ │ 🔍 Search   ⊞ Filter (2)   ↕ Sort   ⊟ Group: Status                │ │
│ └────────────────────────────────────────────────────────────────────┘ │
│                                                                        │
│  Site            Customer         Status     Visited     Amount        │
│  ───────────────────────────────────────────────────────────────────   │
│  Warangal Unit   Sustro Oils      Open       12 Jul      ₹ 45,000      │
│  Vasundhara      The Active Co    Closed     08 Jul      ₹ 12,500      │
└────────────────────────────────────────────────────────────────────────┘
```

The grid is the same visual language as the registry-driven tables — same header
row, same fractional column widths, same badge and money rendering — because to
a user there should be no seam between "a table the developer made" and "a table
I made".

Two editing paths, and both are deliberate:

* **Click a row → entry modal.** The primary path, as specified. Fields grouped,
  labelled, validated, with the same layout as the CRM's create form. This is
  where relation pickers and long text are usable.
* **Double-click a cell → inline edit.** The Excel half of the promise. Tab and
  Enter move between cells. Suppressed for types a cell cannot hold well
  (`longtext`, `attachment`, `relation`), which fall through to the modal.

`⚙ Columns` opens the schema editor — add, rename, retype, reorder, set options,
set width, delete — visible only to a `manager`. `⋯ Settings` holds the rename,
icon, group, visibility toggle, and the sharing list where per-table access is
granted.

Everything above degrades on mobile through the existing `hq-responsive` layer:
the grid becomes stacked cards, the filter bar collapses to a sheet, and the
entry modal goes full-screen.

## Limitations

Stated rather than discovered later.

1. **Relations have no referential integrity.** Ids inside a JSON array cannot
   have a foreign key. A deleted target renders `(deleted)`. Fixing this
   properly means a join table, which means relations stop being a column type
   and become their own subsystem.
2. **Attachments are links, not uploads.** HQ has no upload endpoint; TabDesk
   does not add one.
3. **No formulas, no rollups.** Explicitly out of scope for this build. A rollup
   needs a recalculation graph across relations, which is a larger piece of work
   than everything in this document.
4. **Filtering is slower than a real table.** A JSON extraction cannot use a
   plain B-tree index. At HQ's scale (hundreds to low thousands of rows per
   table) this is not measurable; at a million rows it would be, and the fix is
   a generated column with an index on the hot filters.
5. **No row-level permissions.** Access is per table, not per row. A
   `contributor` editing only their own rows is the closest thing, and it is a
   write restriction, not a read one — everyone with access reads every row.
6. **No realtime.** Two people editing the same row last-write-wins, as
   everywhere else in HQ.
